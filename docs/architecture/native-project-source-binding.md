# Native project source binding v1 — producer/consumer coordination

Producer owner: CAD/project source lane, branch `codex/native-authored-box-20261101`. This document fixes the initial boundary for the exchange owner; implementation and review are in progress. It does not authorize publication or imply a persisted engineering schema already exists.

One selected project scene object, not a mesh ID alone, defines the occurrence. The producer snapshots an actual `ProjectDocument`, resolves the selected `ObjectId`, attached `EditableMesh` and root-object local transform from that same snapshot, and compiles actual triangle/face mapping. Initial supported scope is one root object with a finite rigid transform; parented instances, scale/shear, missing assets and unsupported data refuse. The source is the current native project mesh snapshot, **not evidence of an original parametric box feature or of an imported STEP file**. Multiple scene objects can share a mesh; the selected object ID and transform are always retained separately.

The source projection is non-circular: its canonical bytes identify the project source namespace, selected object ID and name, mesh asset ID, editable mesh revision and `project::canonical_mesh_snapshot_digest`, explicit local-to-project-world rigid transform, and the existing project units `meters` and `right_handed_y_up` convention. The project and scene revisions are reported as observed context but are not part of the projection digest: project updates must not create a self-reference, and scene revision is reconstructed on load. Source review discovered the scene-revision limitation before the producer was committed; this correction supersedes the earlier draft. The producer derives the mesh snapshot digest from actual owner data, not a caller-supplied value. Projection bytes and SHA-256 are retained together; the consumer must recompute from the current project selection and compare before publication. An engineering source revision is a projection digest string, not a cast of the scene, mesh or project revision.

The v1 bytes use the classic C++ locale: `CARTO_NATIVE_PROJECT_MESH 1\n`, namespace and object name with `std::quoted` separated by a space and newline, decimal object ID/mesh asset ID/mesh revision separated by spaces and newline, lowercase editable-mesh SHA-256 and newline, `meters right_handed_y_up\n`, then translation xyz, quaternion xyzw and scale xyz as ten lowercase zero-padded 16-digit IEEE-754 binary64 bit-pattern hex values, each followed by a space, then newline. Project and scene observed revisions are not in those bytes. Consumers should use the owner producer to recompute this exact projection, not independently guess its encoding.

The producer returns the actual geometry `CompiledMesh` for the physical owner and an independently serialized production `RenderMeshArtifact` as a display candidate. The artifact's bytes have their own digest; triangle-to-source-face mappings refer to those exact artifact triangle indices. **The artifact is not registered or verified as the selected project asset's displayed bytes**; `render_asset_binding_verified()` always returns false. The display owner must establish that association separately. The returned record is mutable and is not an admission receipt: the consumer must rederive the complete result from current authoritative project state and use that fresh result, not trust a supplied projection, mesh, map or digest. The physical owner's compiled-mesh digest, surface-domain digest and render-artifact digest have different canonicalizations and must never be equated. The producer does not report a physical result until the physical owner validates the actual compiled mesh, explicit construction/density and rest/state/frame basis. Shape or a render material does not establish composition, mass, pressure, flow or heat.

Engineering topology source keys use the existing `TopologyIdentityKey` and `persistent_topology_id`, with the project source namespace, mesh asset identity and actual authored face ID. The selected object and transform remain occurrence-level binding; they are not inferred from the mesh or topology numeric IDs. Each generated render-artifact triangle has a candidate association with its actual source face and artifact digest. The producer returns candidate bindings, not a directly usable picking map: the display owner must verify the artifact association before constructing and admitting one. Engineering part, occurrence and face records are candidates for a future native-source admission; the existing `admit_extracted_assembly` hardcodes `step_ap242` and **must not be called on this source**. The exchange owner must coordinate a native source kind and versioned persisted linkage while preserving schemas 5–7; this contract does not modify its shared serialization files.

The identifiers above are scoped to the current live project asset. Source review found project and scene next-ID high-water marks are reconstructed after load, so deletion/recreation may reuse a number; equal keys do not prove historical survival without owner-controlled tombstones or lineage. The editable-mesh snapshot digest does not establish persistence of edge/half-edge IDs, which can be reconstructed on load. A consumer must independently rederive and compare the physical owner's complete compiled-mesh digest; neither the source projection nor a matching render face map proves byte-identical physical compiled topology after reopen. These are source-level findings pending integration verification.

The live editing viewport uses `render::RenderInstance` with `CompiledMesh`, not the detached production artifact. `verify_project_viewport_face` rederives the selected project source and compares its object, asset, mesh revision, world transform and every compiled mesh field with an owner-supplied viewport scene, then maps a face present in that compiled instance to its source topology key and actual compiled triangle indices. The caller must supply the real owner-captured scene and protect both inputs from concurrent mutation; a freely constructed `RenderScene` is not authenticated. This checks structural consistency only: it does not prove a user selected the face, pixels were displayed, an artifact is registered, or a physical/inspection result was admitted. The result is point-in-time and must be rederived at use. An application-owner route must additionally validate its current project generation, selection and authority (the existing viewport-decal observation is a precedent). D3D12 saved-scene capture uses a separately generated, material-option-dependent production artifact; its byte binding remains a separate gate. The current viewport check also derives and serializes the detached production artifact, so it can be expensive and may refuse a viewport-valid mesh under production limits; factoring a lighter shared derivation is future work.

Imported unit/metadata, component material domain, original feature operations, temporal intervals/scenarios and execution evidence are unavailable unless an owning record supplies them. A current authored transform is not an observed or executed physical pose. Reimport/topology changes need explicit reconciliation, preserve last-good and stay blocked on ambiguity. Bind real records and owner authority, not labels or digest coincidence.
