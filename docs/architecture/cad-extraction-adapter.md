# STEP extraction candidate boundary

This is a bounded provider-neutral *candidate* adapter, not a connected STEP parser or OCCT implementation. `StepAp242Provider::read_assembly` remains unsupported. An external backend may be supplied to `extract_step_with_backend`; the in-tree test backend is synthetic, and its inputs are not evidence of a real CAD import.

## Requirement and derivation trace

The Cartographer DV012 Engineering Authoring Docuseries defines `SC-01` source/provider identity and loss, `SC-02` stable part and occurrence identity, `SC-03` persistent selectable topology and display mapping, `SC-04` rendered selection to topology, `SC-05` through `SC-08` authoring and publication, and `SC-09` and `SC-10` invalidation and reopen. Its CAD provider chapter calls for a mature kernel, explicit source units, rigid occurrences, topology and display correspondence; it explicitly says not to write a STEP parser from scratch. The local DV012 queue retains production extraction, stable topology, display correspondence and loss-aware reimport as started gates. The bounded code here is a step toward those requirements, not their completion.

The candidate path snapshots bounded source and caller-owned settings bytes, computes the source SHA-256, verifies the settings bytes against the caller-provided SHA-256, and passes exact settings to an injected backend. It checks provider-reported source/settings digests, explicit matching source and coordinate units, stable-identity attestation, supported geometry, external-reference resolution, bounded and valid records, rigid occurrence transforms and acyclic hierarchy. It checks a source/revision/digest-bound `TopologyCorrespondenceMap` against face records and rejects ambiguous display triangles and inconsistent mesh revision/digest assertions. It then feeds the existing `ExtractedAssemblyInput` through `admit_extracted_assembly` and returns the authoring candidate together with the correspondence map. The STEP schema label is retained as a source diagnostic. These comparisons bind supplied evidence; a digest is not a signature, and backend assertions do not prove which settings were executed or that identities are actually stable across independent imports.

The current `TopologyBinding` requires a display mesh asset ID, but neither the adapter nor `TopologyCorrespondenceMap` reads a project's actual mesh bytes or validates triangle ownership. The product is face-only and uses part-level face records; occurrence-specific face mappings, B-Rep bodies/edges/vertices and PMI are not admitted by this slice. Returned candidates are explicitly marked lossy and `display_mesh_content_verified` is false. Existing `admit_for_consumer` refuses a lossy source; raw `InspectionPackage::publish` is a separate operation that does not itself enforce that condition, so callers must not publish the candidate as an accepted result. The separate correspondence map is not serialized by `AuthoringDocument`; durable save/reopen of the full source-to-display chain is still required. Settings bytes likewise remain caller-owned; the authoring record retains their digest only.

First import must be explicitly declared and its newness established by the owning project. Reimport requires the prior correspondence map and uses `compare_topology_reimport` to identify changed or ambiguous correspondence. Even an unchanged map is refused: it cannot establish that prior numeric part, occurrence and topology IDs, transforms or authored bindings remain unchanged. Full prior-authoring reconciliation must preserve existing records, invalidate dependencies and block publication when necessary before any reimport route can be accepted.

`docs/architecture/physical-twin.md` and `collision-representations.md` describe deeper consumers, not data the adapter invents. `physical::derive_geometry_evidence` needs actual validated `geometry::CompiledMesh` data to derive volume, centroid, inertia and a bounds-center face-plane thickness proxy; the proxy is not a physical wall-thickness measurement. `physical::derive_mass` binds that evidence to authored `ConstructionProfile` and material density in a `MassDerivationReceipt`; missing density fails rather than being guessed. Collision representation families derive candidates from the same source identity, measure `CollisionErrorMetrics`, enforce `CollisionErrorThresholdPolicy`, and retain selected/rejected outcomes in `CollisionVariantSelection`. A provider-reported mesh ID or triangle map is not geometry evidence, a mass receipt, a collision certification, clearance or runtime validation. A real implementation must validate source/mesh digests, units/conversion, topology ownership, occurrence placement, winding and compiled geometry before invoking those consumers; material or construction intent must come from an authoritative source or explicit user input.

## Remaining gates

- Connect a mature CAD backend to the neutral extraction contract; do not infer units, names, revisions, stable topology or PMI from a header. The inspected optional VANTA OCCT implementation flattens assembly shapes and does not provide the full source/unit/occurrence identity required here; its per-load topology ordering is not demonstrated to be stable across independent imports.
- Validate exact source and settings, actual mesh bytes/digests, triangle bounds and face ownership; persist the full map and source settings needed for deterministic reopen. Handle occurrence-specific mappings, source and coordinate unit conversion, body/edge/vertex topology, and source-specific stable identities.
- Implement full source/authoring reimport reconciliation, preserving requirements and rejecting or marking stale changed/ambiguous bindings; prevent publication at the owning workflow until complete evidence is accepted.
- Run real retained STEP assembly fixtures through a supported backend and check hierarchy, transforms, units, topology, tessellation, source-face selection, loss reports, save/reopen and deterministic receipts. Separately derive and validate physical evidence, construction/mass and collision candidates from real compiled geometry under their existing contracts.
- Keep sensor, motion planning, collision execution and runtime admission with their owning consumers; a fixture result is not hardware, simulation, deployment or runtime acceptance.
