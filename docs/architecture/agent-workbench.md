# Agent Workbench: speculative authoring slice

## CONDITION evidence audit

The desktop can summarize current/reviewed source lineage and metadata scan completeness, then perform bounded factual checks against the project's current mesh data. A gate report labels the observed source-lineage, metadata-scan, mesh-validation, render-UV-presence, and material-region-assignment checks as passed, failed, incomplete, or unavailable. Each gate keeps its observed scope separate from assets with failed, unavailable, or asset-level incomplete evidence. Truncated and mixed queries cannot turn observed passes into complete-scope passes. It separately labels tangent validation, bake freshness, collision, traversal, anchor validity, source-to-geometry/material digest correspondence, and CONDITION policy as not evaluated. These bounded checks do not establish CONDITION readiness: the query does not compare source digests with current geometry or materials, inspect tangents or bake freshness, validate collision or traversal, or apply domain-specific CONDITION policy.

## Capability

Cartographer can capture a goal and a bounded sequence of exact object, face, vertex, explicitly permitted material-region, and explicitly permitted lightmap-UV operations, execute the native proposals on a private copy of the current project, validate the branch, and present a structured diff for review. One ordered DAG can compose geometry, material assignment, and UV generation while each non-default effect remains separately granted by the work envelope. Material assignment binds an existing material and optional variant to an explicitly named face-region ID on the selected mesh. Lightmap generation adds a deterministic, revision-bound corner UV layer and marks its new set as a candidate; it leaves existing UV sets and topology intact. Material and UV effects are opt-in, shared mesh instances must all be in-scope, unprotected, and unlocked, and the source project stays unchanged until a user accepts the result. A generated candidate is not a claim of production readiness. The task also exposes bounded read-only queries over the branch for scoped object identity, exact names, mesh instances, object-origin proximity, face orientation, boundary edges, CONDITION tags, familiarity records, per-asset CONDITION metadata counts, and limited mesh/UV/material-reference checks. CONDITION facts carry source identity, source revision, current/reviewed state, and protected features where applicable; stale or unreviewed evidence is returned as such, not presented as current. Mesh/UV/material results have explicit passed, failed, incomplete, or unavailable states and do not establish CONDITION production readiness.

The native planner supports face inset, face extrusion, parameterless face poke, vertex positioning, bounded root-object translation, exact material assignment intents of the form `assign material <id> to region <id> [variant <id>]`, and lightmap UV intents of the form `generate lightmap uv set <id> resolution <pixels> padding <texels> tiles <count>`. IDs are parsed as unsigned integers without floating-point conversion. Material assignment and UV generation require their separate effect permissions and always remain review-only. The UV generator accepts bounded planar faces and fails when the requested atlas budget cannot fit. The planner does not call an external model or infer targets. The user captures each target from the normal viewport selection path.

## Authority path

```text
captured targets + goal
    -> AgentPlan + AgentWorkEnvelope
    -> private ApplicationSession copy
    -> scoped SceneQuery facts + read-budget ledger
    -> NativePlanner proposal
    -> revision-bound AuthoringPreview
    -> native application command on the copy
    -> project / viewport / plan / diff gates
    -> explicit user accept
    -> source revision check + application journal event
```

The speculative application copy has no project path or journal binding. It cannot save, publish, or mutate the source. Acceptance rejects a stale source revision, validates the complete candidate, resets the candidate's project revision to one step after the source, and writes one application mutation snapshot with the task ID and diff digest before publishing it in memory. A failed journal append restores the source document. The accepted snapshot is one undoable application command; because it replaces complete project state, prior command undo/redo history is replaced by that single result command.

## Work envelope

The envelope limits commands to captured object IDs, geometry/topology and explicitly granted material/UV effects, at most 16 commands, a bounded touched-object count, and total topology churn. Material assignment and UV generation each require a separate effect permission; neither is reachable through the generic AI proposal boundary. The selected UV target must have a mesh with no existing output set or layer identity, and every shared-mesh instance must be in-scope, unprotected, and unlocked. The generated set is a non-active lightmap candidate; the operation does not modify existing UV data. Root-object translation requires a separate transform effect permission and a finite cumulative displacement bound in meters. It is limited to one root target and its complete descendant subtree, within the touched-object budget; every affected object must be in scope, unprotected, and unlocked. Translation preserves local rotation and scale, and the source remains unchanged on the speculative branch until acceptance. Generic AI proposals continue to receive only geometry/topology capabilities; object translation, material assignment, and UV generation are exposed only through the Agent Workbench envelope. Topology churn counts added/removed mesh assets, vertices, and faces plus face-connectivity changes; exceeding the limit blocks acceptance and records a diagnostic. Read budgets independently cap query count, objects examined, topology elements examined, semantic records examined, and result bytes. Repair budgets cap retries and additional operations. Queries return copied facts at a source revision and filter results to the objective scope. Protected object IDs are rejected during plan validation. Because Cartographer can share one mesh asset across several scene objects, every instance of a target mesh must also be inside scope and unprotected; the touch budget counts all affected instances. The planner only emits registered typed proposals, and each proposal must pass its current native ontology and preview validation.

The native capability registry describes every registered mesh command with typed parameter bounds and units, target/read/write shapes, effects, invalidations, validators, reversibility risk, and advisory cost hints. Four mesh operations have native preview contracts (face inset, face extrusion, parameterless face poke, and vertex positioning); the production lightmap generator also has a typed revision-bound preview contract. Face poke, root-object translation, material assignment, and UV generation require explicit review and are not auto-approvable. Accepted face-poke demonstrations retain a parameterless typed value and are versioned separately from older demonstration files. The workbench projects that registry through the task's effect mask and exposes only previewable capabilities whose effects fit the envelope. Cost hints describe expected work; query and touch limits remain the enforced budgets. A registry entry never contains a command callback or a document reference.

An operator can compose captured mesh operations, root-object translation, exact material-region assignment, and lightmap UV generation across separate selected targets in one DAG when the exact target scope and combined geometry/topology/transform/material/UV envelope are supplied. Material and UV changes are surfaced in the review diff; CONDITION mutation remains outside the verified plan surface.

Objectives can carry hard constraints for preserving topology, preserving an object's world transform, or limiting world-space vertex displacement. Displacement gates compare every stable vertex correspondence, include object world transforms, and fail closed when topology cannot be matched or the measurement budget is exceeded. Constraint gates block acceptance, and topology preservation rejects a conflicting command before it runs on the speculative branch. A deterministic clarification frontier ranks declared questions by the consequences they affect and the number of downstream branches. High-impact unresolved questions block task creation; questions explicitly marked as operator-required also block regardless of score. Candidate choices are checked against queued targets. The native workbench can collect an operator-authored question with bounded candidate labels or a freeform answer, then record the operator's choice against the exact goal, target scope, objective revision, question context, and ordered plan steps/dependencies. Before answering, the Agent workspace shows the operator rationale, consequence categories, affected-object count, and downstream branch count; expandable scope rows expose object IDs, including each candidate's mapping. Only the human application boundary can issue the answer receipt. A choice adds no plan steps or scope; any changed plan invalidates the answer receipt and requires reconfirmation. Answers appear in the review snapshot and acceptance digest. The system still does not infer objective meaning or generate questions from free-form goals.

The objective compiler is deliberately narrow: it accepts only three explicit constraint grammars: topology preservation, unchanged world transforms, and a positive maximum vertex-displacement bound with an explicit world-units suffix and requires every compiled hard constraint before clarification receipts are issued or tasks are created. Objective validation also requires the generated constraints, so direct plan construction cannot bypass the compiler. The desktop goal editor previews this limit and disables Run when the compiler cannot enforce an explicit restriction. Unsupported restrictions and conflicting topology requirements fail closed; the compiler does not map arbitrary language to structured constraints, interpret general goal meaning, or generate questions.

The Agent goal editor can compile an explicit sequence of supported native commands, separated by `then` or semicolons, into a bounded DAG. A single object, face, or vertex target produces one ordered chain; selecting multiple unlocked root objects produces one independent ordered chain per root, with the total expanded plan capped at 16 steps. The explicit prefix `on object "Exact Name":` resolves through a bounded, revision-bound exact-name `SceneQuery`. A unique unlocked root overrides the current selection; duplicate names require exactly one matching unlocked root selected, and only that selected identity enters the plan and work-envelope scope. The explicit prefix `on nearest object within <radius> world units of "Anchor":` resolves the nearest object origin around a uniquely named anchor through bounded, revision-bound SceneQueries. The radius must be positive and at most 1,000,000 world units; tied nearest candidates, locked/nested nearest targets, and incomplete or stale queries fail closed without selection fallback. The explicit prefix `on CONDITION tag "Exact Tag":` resolves all unique authored objects for that exact tag through the bounded, revision-bound CONDITION SceneQuery. It requires current, reviewed source evidence, rejects objects carrying protected features until feature-level preservation constraints exist, and rejects locked/nested targets, missing sidecars, unknown tags, incomplete results, or more than 16 objects without selection fallback. Only resolved roots enter plan and work-envelope scope. Escaped quotes and backslashes are supported in scoped names and tags. Each command is validated against the native preview ontology at the captured source revision. Compilation only creates a reviewable plan draft; it does not execute native commands. Unsupported clauses, extra instruction text, empty clauses, nested or locked object targets, or an expanded plan over 16 steps fail without installing a partial draft. General semantic objective planning and ranked clarification generation remain future work.

Plan steps may depend on earlier captured steps. Validation rejects missing, duplicate, self, and cyclic dependencies. A stable topological scheduler executes one native command at a time within the command budget. When a step fails, its dependent branch is marked invalidated while independent ready steps may continue on the private project copy; any failed or invalidated step blocks acceptance. A blocked attempt can be repaired only with an operator justification and a revised plan that preserves the objective context and object scope while keeping every envelope limit the same or narrower. Repair always starts from a fresh copy of the unchanged source. It retains the earlier step receipts, gate results, and evidence digests in the repair chain. Changing a plan invalidates its human clarification receipts; the operator must answer again against the repaired plan before execution. Retry and added-operation budgets are cumulative across the repair chain. The Agent workspace can select and revise a same-object step, re-answer invalidated questions, and shows the final branch state and prior failure evidence.

When a task is active, non-Agent authoring workspaces show a persistent status strip with task identity, step and required-gate counts derived from current receipts, and a route back to the Agent workspace. Blocked and review-ready tasks remain visible until accepted or rejected. The strip is a presentation projection; it does not add mutation or acceptance authority.

The shell header also exposes an “Ask Cartographer” entry from the project surfaces. It opens the Agent workspace, reveals the Agent Workbench instrument, and focuses the goal field; it does not create a plan or start execution. Each Scene outliner row has a context-menu action that selects that object and opens the same goal editor. Existing component selection is preserved when the operator moves between the available workspaces. The Review workspace opens the same Agent Workbench on the speculative after branch, and the persistent task strip routes review-ready tasks there.

The CONDITION workspace offers a read-only inventory action for the current object selection; it returns copied facts at the captured project revision and does not create a task. The Agent workspace also offers a two-stage path for planned work: prepare the task at the captured source revision, inspect its task-scoped inventory, then explicitly run the prepared plan. Preparation locks the goal and work envelope but does not execute native commands. Running rechecks the source revision; a concurrent project edit leaves the task prepared and requires a fresh task. The existing one-click speculative run remains available when the operator does not need a preflight query. Cached inventory is hidden when its source revision or selection scope no longer matches.

The Material workspace can draft its selected material and region as a native Agent plan. It accepts one to sixteen unlocked root mesh objects only when every instance of each selected shared mesh is included. The exact material ID and non-zero region ID are captured in the goal, the material effect is enabled for the later work envelope, and the Agent workspace opens on the compiled draft. This entry action does not mutate the project; preparation, execution, review, and explicit acceptance remain separate. If multiple selected objects share one mesh and request the same assignment, the first step performs the mesh/region write and later identical steps receive passed no-op receipts only after the prior write is verified. Checkpoint resume replays this behavior.

The UV workspace can draft the lightmap-candidate UV operation for one to sixteen unlocked root objects whose mesh assets are unique in the scene. The operator supplies the new set ID, resolution, padding, and tile limit; the UI grants only the UV effect and compiles the goal before routing to Agent. An occupied ID or atlas that does not fit fails during native preview. The candidate remains non-active and does not establish seam quality, bake freshness, or production readiness. Shared mesh UV authoring through this entry point remains disabled until it has a single-write multi-instance plan representation.

The Sculpt workspace exposes a target-preserving handoff to the Agent workspace for supported native mesh plans. It does not claim that Agent tasks can author SculptStack layers, masks, remesh, or multires settings. Material-graph actions and wider CONDITION authoring actions remain future workspace-specific integrations.

## Review evidence

The review view includes source/before/after viewport modes, per-step receipts, required gates, changed object and mesh records with vertex positions and face connectivity, generic attribute-layer change counts, typed UV-set descriptor changes and stable-corner coordinate samples, material-region assignments with before/after material and variant identities, changed base-material and texture-source records, and a material-catalog change flag for records not expanded in this view. Variant, sampler, graph, and blob records are not yet shown as detailed rows. Engineering/CONDITION sidecar changes appear as flags. The view also includes a SHA-256 digest of the complete serialized branch result. UV diffs count every changed corner while retaining at most 256 coordinate samples per set; the UI labels omitted samples and preserves the full count. Every gate also carries its validator version, source and evaluated revisions, affected objects and assets, result digest, canonical evidence digest, and any diagnostic. The digest binds the gate outcome and evidence to those identities and revisions. Branch viewport modes are read-only and disable source selection. Required gates are project validity, viewport compilation, all plan steps passing, and a non-empty diff. Whole-result acceptance is explicit.


## Recorded demonstrations

An operator can save a human-accepted task as an immutable `.carto-agent-demo` record and open it for read-only inspection. Format v2 adds typed, transferable parameters: face distances are ratios of the source face's longest edge, and vertex/object movement is a relative displacement. It never stores absolute vertex or world positions. The record also contains recipe identity, objective and diff digests, passing tool IDs, per-record object aliases, relative revision offsets, validator IDs and versions, gate evidence digests, and bounded repair/rebase/ghost-correction counts. It omits project bytes, real object and asset IDs, names, goals, step text, clarification prompts and answers, diagnostic messages, and filesystem paths. Format v1 records remain readable but have no typed parameters. The record is not an AgentPlan and cannot be replayed or accepted. Its checksum detects accidental corruption; it does not authenticate authorship. Digests may still be matched against known inputs, so the artifact should be reviewed before sharing.

## Deliberate limits

“Apply to selection” supports 1–16 explicit target sets. Each set receives a complete alias mapping and becomes an independent ordered trace chain in one bounded speculative plan. Direct targets and hierarchy-expanded scopes must be disjoint across sets, and the expanded plan is limited to 256 steps. All chains share the existing validation gates, diff review, and human acceptance boundary. “Apply to similar” supports a single captured command, a multi-command root-object translation chain with unchanged structural signatures, or repeated vertex-position changes to one aliased vertex when every pre-component signature and post-object signature stays stable. It verifies the completed exemplar, excludes it from targets, requires one unique component match per candidate object, skips ambiguity, omits shared mesh assets across target sets, and caps results at 16. Each repeated vertex displacement is applied in sequence on the speculative branch. These bounded summaries are not a full graph-isomorphism proof. The trace stores only hashes of the structural features, never scene identities, names, coordinates, or transforms. Semantic, prefab, material, socket, and spatial-role matching remain unsupported.

SceneQuery is intentionally a small typed vocabulary. CONDITION inventory returns per-asset counts for authored profiles, familiarity, views, variants, temporal packages, surface states, anchors, and collection/prefab/kit membership; it does not expose those containers' names or nested contents. It also reports bounded mesh validation, active render UV and lightmap-candidate presence, and whether declared material regions have explicit catalog assignments. These are technical observations and do not establish overall readiness. Query results are read-only and revision-bound; missing CONDITION data is reported as unavailable, and stale CONDITION revisions fail closed. It does not expose viewport visibility, UV seam quality, tangents, bake freshness, collision, traversal, arbitrary predicates, or provider-side document access. Repair is operator-directed replanning, not autonomous model repair: the native workbench does not infer a correction, add scope, or relax constraints. Persistent checkpoints and conservative read/write-set rebase are implemented for the current geometry/topology/transform, UV, and material-region assignment plan surface. Human ghost correction supports scoped root-object transforms, vertex positions, and native face inset/extrusion on the speculative after branch. Vertex and face edits require every instance of a shared mesh to be in-scope, unlocked, and unprotected. Face corrections require a positive finite distance, geometry and topology effects in the work envelope, and no applicable preserve-topology constraint. Each correction requires operator justification, becomes immutable task evidence, re-runs acceptance gates, and is replayed through checkpoint resume, rebase, and bounded repair. Mesh corrections bind canonical before/after mesh digests; replay blocks when the native result differs. Corrections remain separate from planner translation, which requires an explicit transform envelope. Corrections are anchored to the last completed plan step that wrote the target and replay its transitive dependents in topological order; corrections without an earlier writer replay after the plan. A bounded recompute receipt preserves prior step and gate evidence and binds the correction, anchor, dependent IDs, before and after diff digests and revisions, and replay result. Checkpoint v8 stores anchors, the recompute budget, and this lineage; checkpoint v9 adds reused-step IDs to rebase lineage, and checkpoint v10 adds material-region read/write keys. Checkpoint v11 persists consumed SceneQuery counters within their immutable work-envelope limits. Versions 1 through 10 remain readable; older checkpoints have no saved query-usage counters. Built-in recipes keep operator-authored steps and do not infer objectives or generate plans. `bounded-mesh-edit` applies a 512-operation topology cap, rejects transform permission, and requires stable scene-object identity. `bounded-vertex-edit` permits geometry effects only, sets the topology budget to zero, and requires both stable scene-object identity and unchanged vertex/face topology; the same recipe limits are reapplied during repair and validated in saved checkpoints. Recipe identity participates in objective and clarification digests and persists in checkpoint format v7. In addition to accepted-task records, the desktop can capture contiguous ranges from a bounded, in-memory trace of supported human native edits: face inset/extrude, vertex-position changes, and root-object translation. The exported trace replaces object and component IDs with within-record aliases and stores normalized face distances or relative displacements. Trace v2 may also contain topology-only SHA-256 signatures derived from mesh counts, face arity, and local incidence; it stores no source IDs, names, coordinates, or transforms. Unsupported project-changing edits clear the recent trace. A trace file alone is inspect-only: the UI requires explicit current-target bindings before it builds a bounded AgentTask. “Apply to similar” supports any single captured command, root-object translation chains to the same alias with unchanged structural signatures, and repeated vertex-position changes to one aliased vertex when pre-component and post-object signatures remain stable. It verifies a selected completed exemplar against its post-command object evidence, finds pre-command structural-signature matches, and skips objects with ambiguous component matches. Repeated displacements use the previous speculative position, and shared mesh assets across target sets remain excluded. These bounded summaries are not a full graph-isomorphism proof. Semantic, prefab, material, socket, and spatial-role matching remain unsupported. Preview resolves normalized face distances against the selected face's boundary edge length and vertex displacements against the selected vertex, executes the bounded plan on a speculative branch, and presents the existing validation gates and diff. The source stays unchanged until the separate human acceptance action. Bindings expire when the source revision changes. Named demonstration recipes wrap redacted traces without target bindings or task authority. Remaining work includes broader objective compilation and question generation, broader multi-domain capability composition, further recipes and project standards, workspace-specific authoring actions, and full integration across authoring workspaces. For disjoint changes with no invalidated plan steps, rebase reproduces the checkpoint on its historical source, merges verified declared writes onto the current document, and records reused step IDs; the live source remains unchanged until explicit acceptance. When read-only object inputs change, rebase re-executes the affected DAG branches and dependents while reusing verified steps with unique, disjoint write sets. Changes to mesh write targets, object write targets, shared-mesh membership, or semantic sidecars block rebase. Plans with material assignment steps use full native replay when any step is invalidated; plans with overlapping step write sets and checkpoints with ghost corrections also retain the full native replay path.

Material-region assignment checkpoints record mesh and region keys and depend on the saved material and variant sources. Rebase preserves assignments at other keys but blocks a changed written region, changed material source definitions, or a changed mesh. Material writes remain on the reviewed speculative branch until explicit acceptance. An accepted material-assignment task cannot be exported as a transferable demonstration until the demonstration format can bind material and region aliases without copying source IDs.
